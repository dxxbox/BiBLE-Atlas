# FastAPI 架构总览（v4）

本文档定义 v4 的目标架构。核心目标是在保持功能完整的前提下，降低类型分支复杂度，并把 API、Feature、Infrastructure 的边界进一步拉清。

---

## 1. 设计原则

### 1.1 仓储类型收敛

v4 只保留三类业务仓储：

- `KNOWLEDGE_BASE`
- `SKILL`
- `MEMORY`（由 v3 的 `SESSION` 重命名）

历史类型归并规则：

| v3 类型 | v4 类型 | 说明 |
|---|---|---|
| `CODE` | `KNOWLEDGE_BASE` | 合并到统一知识库域 |
| `SCT` | `KNOWLEDGE_BASE` | 合并到统一知识库域 |
| `ALG` | `KNOWLEDGE_BASE` | 合并到统一知识库域 |
| `DESIGN` | `KNOWLEDGE_BASE` | 合并到统一知识库域 |
| `FLOW` | `KNOWLEDGE_BASE` | 合并到统一知识库域 |
| `SYNTAX` | `KNOWLEDGE_BASE` | 合并到统一知识库域 |
| `BUILD`/`BUIL` | `KNOWLEDGE_BASE` | 历史别名兼容 |
| `SKILL` | `SKILL` | 保持不变 |
| `SESSION` | `MEMORY` | 类型重命名 |

### 1.2 API 按能力 + 业务域双维拆分

- 能力维：`search/import/download/control`
- 业务域维：`knowledge_base/skill/memory`

不再使用 v3 的“单 search/import/download 入口 + doc_type 分发”模型。

### 1.3 Feature 去 Repository 化

v4 在 `app/features/` 内不再使用 `repositories/` 目录，也不再有 `code.py/sct.py/alg.py` 这类类型仓储文件。  
每个 feature 子域改为固定三段式：

- `service`：处理 API 请求的总入口
- `parser/searcher`：领域核心逻辑
- `storage`：入库与持久化编排

## 3. 分层职责

### 3.1 API 层（`app/api/`）

- 仅负责 HTTP 入参校验、鉴权、调用 service、输出响应
- 按能力分目录（`search/import/download/control`）
- 每个能力目录下按业务域拆分独立 API 文件
- 不包含业务编排和数据库实现细节

### 3.2 Feature 层（`app/features/`）

- 每个子域以 `{domain}_{capability}_service.py` 作为总入口
- `async_task/` 作为通用异步能力层（Celery 提交、状态查询、执行器注册）
- import 子域统一采用：`service -> parsers/parse_*.py -> storage.store`
- search 子域统一采用：`service -> searcher.search`
- 不直接暴露底层数据库 SDK 或文件系统细节给 API 层

### 3.3 Infrastructure 层（`app/infrastructure/`）

- `database/`：封装统一数据库接口与多后端适配实现（如 `database/opensearch/`、`database/elasticsearch/`、`database/postgres/`）
- `file_system/`：封装文件系统/对象存储接口（替代 v3 `storage/`）
- `features/upload/parser_runtime/`：负责导入阶段的脚本安全检查与沙箱执行
- `vector/`：负责向量模型生命周期（本地检查、缺失下载、启动预加载）与文本向量化

## 4. 主流程

### 4.1 import 流程（以 `skill_import` 为例）

1. `skill_upload_api.py` 接收上传请求
2. API 做入参校验后调用 `features/async_task/service.py` 提交任务（`task_type=import.skill`），立即返回 `202 + task_id`
3. Celery Worker 消费任务，通过 `features/upload/upload_task_executor.py` 调用 `skill_upload_service.py`
4. `skill_upload_service.py` 选择解析脚本并调用 `SandboxRunner` 执行：
   - 本次请求上传的脚本先从任务临时目录执行，导入成功后才原子覆盖保存到 `custom_parsers_dir/parse_skill.py`
   - 未上传脚本时优先使用 `custom_parsers_dir/parse_skill.py`，再回退到预注册 `parsers_dir/parse_skill.py` / `parse_default.py`
5. `storage/store_skill.py` 在入库前处理向量化：
   - 若请求带 `vector_model`：调用 `infrastructure/vector/vector_tool.py` 检查本地模型，缺失则从 HuggingFace 下载，再生成 `content_vector`
   - 若未带 `vector_model`：跳过向量化
6. 同时调用 `app/infrastructure/file_system/` 保存原始上传文件
7. `storage/store_skill.py` 通过 `database/` 写入结构化数据（含可选向量字段）

`memory_import` 与 `skill_import` 流程一致（同样“写数据库 + 文件落盘”）。  
`knowledge_base_import` 也遵循 `parse/store` 模式，但是否落盘可按配置策略决定。

### 4.2 search 流程（以 `skill_search` 为例）

1. `skill_search_api.py` 接收检索请求
2. `skill_search_service.py` 处理请求并做参数编排
3. `searcher/search_skill.py` 的 `search` 负责构建查询并调用 `database/` 网关

`memory_search` 与 `knowledge_base_search` 使用相同骨架，不同点只在域内策略实现。  
底层数据库由 `database/factory.py` 选择具体适配器（如 `database/opensearch/`），不影响 feature 层接口。

### 4.3 download 流程

- 只支持 `SKILL` 与 `MEMORY`
- `skill_download_api.py` / `memory_download_api.py` 对外提供 `single/batch` 两类任务提交接口（统一异步）
- API 校验参数后调用 `features/async_task/service.py` 提交任务（`task_type=download.*`），立即返回 `202 + task_id`
- Celery Worker 执行下载任务：通过 `database + file_system` 读取文件并生成 artifact（单文件或 ZIP）
- 客户端通过通用任务查询接口轮询状态，完成后调用 artifact 拉取接口获取文件流
- `KNOWLEDGE_BASE` 不提供 download 功能
- `by-search` 下载不在当前范围，作为后续演进能力

### 4.4 control 流程

v3 中 `app/api/v1/` 下的：

- `docs_api.py`
- `statistics_api.py`
- `admin_api.py`

统一迁移到 `app/api/control/`，并由 `features/control/` 对应 service 处理。

### 4.5 启动预加载流程（向量模型）

1. `main.py` 启动时加载 `application.yaml`
2. 若配置开启 `vector.preload_on_startup`：
   - 调用 `app/infrastructure/vector/model_preloader.py`
   - 遍历配置中的可用向量模型
   - 逐个执行“本地缓存检查 -> 缺失则 HuggingFace 下载 -> 预热加载”
3. 若配置关闭：跳过预加载，导入时按需加载模型

## 5. KNOWLEDGE_BASE 统一类型下的差异化处理

v4 删除了 `repositories/code.py/sct.py/alg.py...` 后，`KNOWLEDGE_BASE` 的“子类型差异”不再通过文件分叉实现，而改为“解析策略 + 检索策略”双驱动。

### 5.1 import 时差异化

- 上传时可选附带自定义解析脚本
- 若未附带脚本，在对应域 `parsers/` 查找 `parse_{tag}.py`，未命中再走默认解析脚本
- 默认解析脚本与自定义脚本必须遵循同一 `parse` 契约（`chunks + search_profile`）
- `search_profile` 绑定与内容写入收敛在 `storage/store_knowledge_base.py`，不再单独拆 `search_profile_store.py`
- `kb_index` 与 `parser/search_profile/vector_model` 首次导入时绑定，后续不可修改（删除索引后可重建）

### 5.2 search 时差异化

- import 阶段会产出并固化绑定 `search_profile`
- search 阶段按 `tag` 读取绑定记录，获取 `kb_index + search_profile` 后动态构建查询
- 由此替代 v3 “按 doc_type 选择不同 repository”的分支模型

## 6. v4 的关键收益

- 类型体系从多类型扁平枚举收敛到 3 个一级域，扩展成本更低
- API 路由和 Feature 目录一一对应，定位问题更直观
- 删除 `v1` 目录和多仓储工厂后，调用链更短
- `KNOWLEDGE_BASE` 支持“默认解析 + 自定义解析脚本”，同时具备强安全边界
- `file_system` 命名更贴近职责，避免与业务层 `storage/store_*.py` 混淆
