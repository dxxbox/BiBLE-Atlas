# v4 关键设计补全与风险清单

本文档基于最新补充要求，对 v4 关键设计进行定稿与架构审视。

---

## 1. 关键设计定稿（按 1.1~1.5）

### 1.1 P0：解析契约与现网导入字段不一致

定稿结论：

- v4 不以兼容当前工程导入字段为目标
- 当前工程仅作为参考，不是约束
- v4 以统一 `parse` 契约为唯一标准（`chunks + search_profile`）

设计要求：

- 默认解析脚本、上传自定义脚本、`skill_upload/parsers`、`memory_upload/parsers` 必须同一函数签名与返回格式
- 导入与检索逻辑只依赖 v4 契约，不依赖旧字段结构

### 1.2 P0：`search_profile` 持久化方案（具体）

### 方案选择

对外统一通过 `infrastructure/database/` 存取绑定关系：

- `kb_index`
- `tag`
- `parser_script`
- `search_profile`
- `vector_model`

### 结构设计（核心）

`v4_index_binding`（见 `03` 文档默认实现示例）用于保存有效绑定，关键点：

- `_id = {domain_type}::{kb_index}` 保证同一物理索引唯一绑定
- `domain_type + tag + is_active=true` 由应用层查重保证唯一
- `search_profile_json` 持久化为对象字段
- `search_profile_sha256` 用于校验一致性

### 写入策略

1. 首次导入某 `kb_index`：
   - 选择最终解析脚本
   - 生成 `search_profile`
   - 通过 `database/` 写入绑定文档（不可变）
2. 已存在绑定：
   - 仅允许导入数据
   - 若请求参数与绑定不一致，直接返回冲突错误

### 读取策略（检索）

1. 根据 `domain + tag` 查到绑定记录
2. 拿到 `kb_index + search_profile + vector_model`
3. 编译 DSL 并检索

### 版本策略

- 不做 `search_profile` 版本演进
- 已存在绑定不可修改
- 若需要变更，必须删除索引并重建绑定

### 1.3 P0：自定义脚本安全边界（具体限制）

定稿限制（必须全部启用）：

- 文件限制：
  - 仅 `.py`
  - 单次仅 1 个脚本
  - 最大 256KB
- AST 限制：
  - 仅允许顶层 `import/常量/parse`
  - 禁止 `ClassDef/Lambda/With/Async/Try/Global/Nonlocal/Delete/Yield`
  - 导入白名单：`json/re/math/datetime/typing/collections/itertools`
  - 调用黑名单：`eval/exec/compile/open/input/__import__/globals/locals`
  - 属性黑名单：`*.system/*.popen/*.fork/*.spawn/*.remove/*.unlink/*.rmdir/*.chmod`
  - 禁止访问 dunder 属性
- 运行限制（容器）：
  - 非 root
  - 无网络
  - 只读根文件系统
  - CPU 1 核、内存 256MB、进程数 64、超时 10 秒/文件
- 输出限制：
  - 最多 5000 chunks
  - chunk 内容最大 32KB
  - 总输出最大 10MB

### 1.4 P1：`KNOWLEDGE_BASE` 下载能力

定稿结论：

- `KNOWLEDGE_BASE` 不支持下载
- 下载相关设计不纳入 v4 范围

### 1.5 P1：`SKILL/MEMORY` 双写一致性

定稿结论：

- 当前阶段不实现双写一致性治理
- 但必须具备完整日志，支持问题回溯和人工修复

日志最小字段：

- `request_id/domain_type/kb_index/tag`
- `parser_script_sha256/search_profile_sha256/vector_model`
- `file_name/database_write_status/file_write_status`
- `error_code/error_message/duration_ms`

## 2. 架构师审视（重点：自定义解析导入与检索）

### 2.1 方案优势

- 通过统一 `parse` 契约，把“文档差异”收敛到解析层
- 通过索引绑定机制，保证检索行为稳定可复现
- 通过脚本选择策略（上传优先 -> 目录发现 -> 默认），兼顾灵活性与可控性
- 三域 API 独立，便于后续按域演化

### 2.2 主要风险点与补齐要求

### 风险 A：`kb_index` 与 `tag` 语义混淆

补齐：

- 在 API 文档中固定语义：
  - `kb_index` = 物理索引
  - `tag` = 逻辑标签（绑定键）
- 服务端严查映射冲突

### 风险 B：目录发现脚本的结果不确定

补齐：

- 域内 `parsers/` 的选择顺序必须固定：上传脚本 > `parse_{tag}.py`（或固定脚本）> `parse_default.py`
- 命中脚本后记录 `parser_script_source/path/sha256`
- 同一次请求禁止多脚本命中后二义选择

### 风险 C：绑定不可变带来的运维成本

补齐：

- 提供标准“删索引重建绑定”流程
- control 接口返回冲突原因和当前绑定信息

### 风险 D：`search_profile` 过度表达

补齐：

- 增加 profile 字段白名单
- 编译器只接受白名单字段，拒绝未知字段

### 风险 E：向量模型冷启动与下载不确定性

补齐：

- 导入时按统一链路执行：本地模型检查 -> 缺失从 HuggingFace 下载 -> 向量化
- 启动时由 `infrastructure/vector/model_preloader.py` 按配置可选预加载模型
- 对模型就绪失败场景输出明确错误码和日志（模型名、来源、失败原因）

## 3. 必须新增的实现组件

1. `knowledge_base_upload_service.py` / `skill_upload_service.py` / `memory_upload_service.py`：提供解析脚本选择链路；其中 `SKILL/MEMORY` 需要支持 `custom_parsers_dir` 优先级与成功后原子覆盖上传脚本
2. 各域导入 service 内的解析结果契约校验逻辑：校验 `chunks + search_profile` 结构
3. `store_knowledge_base.py`：统一处理绑定读写与内容入库（不单独拆 `search_profile_store.py`）
4. `query_profile_compiler.py`：`search_profile -> DSL`
5. `parser_audit_logger.py`：脚本执行与导入日志落统一数据库审计索引
6. `database` 适配分层：`database/base.py + database/factory.py + database/opensearch/`（后续可扩展 `elasticsearch/postgres`）
7. `infrastructure/vector/vector_tool.py`：向量模型就绪检查与 `chunks` 向量化
8. `infrastructure/vector/model_preloader.py`：按配置启动预加载向量模型

## 4. 落地优先级

### Phase A（先闭环）

- 统一 `parse` 契约
- 脚本选择器 + AST/容器执行
- 绑定持久化 + 检索读取

### Phase B（稳定性）

- 日志与审计查询
- 冲突处理与运维工具
- profile 白名单与编译器健壮性
