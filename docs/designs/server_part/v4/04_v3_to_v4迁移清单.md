# v3 -> v4 迁移清单

本文档用于指导从 v3 架构平滑迁移到 v4。

---

## 1. 类型体系迁移

### 1.1 枚举映射

| v3 类型 | v4 类型 | 迁移动作 |
|---|---|---|
| `CODE` | `KNOWLEDGE_BASE` | 更新类型映射与统计口径 |
| `SCT` | `KNOWLEDGE_BASE` | 更新类型映射与统计口径 |
| `ALG` | `KNOWLEDGE_BASE` | 更新类型映射与统计口径 |
| `DESIGN` | `KNOWLEDGE_BASE` | 更新类型映射与统计口径 |
| `FLOW` | `KNOWLEDGE_BASE` | 更新类型映射与统计口径 |
| `SYNTAX` | `KNOWLEDGE_BASE` | 更新类型映射与统计口径 |
| `BUILD`/`BUIL` | `KNOWLEDGE_BASE` | 兼容历史别名 |
| `SKILL` | `SKILL` | 保持不变 |
| `SESSION` | `MEMORY` | 重命名并迁移接口参数 |

### 1.2 历史数据过渡建议

- `legacy_doc_type` 仅作为迁移窗口期的历史字段（可选），不作为 v4 契约字段
- 对外统一展示 `domain_type`（`KNOWLEDGE_BASE/SKILL/MEMORY`）
- 统计报表从“多仓储类型统计”改为“三级域统计 + 子类型维度统计”

## 2. API 结构迁移

### 2.1 路由层目录迁移

| v3 路径 | v4 路径 |
|---|---|
| `app/api/v1/search_api.py` | `app/api/search/knowledge_base_search_api.py` + `skill_search_api.py` + `memory_search_api.py` |
| `app/api/v1/upload_api.py` | `app/api/upload/knowledge_base_upload_api.py` + `skill_upload_api.py` + `memory_upload_api.py` |
| `app/api/v1/download_api.py` | `app/api/download/skill_download_api.py` + `memory_download_api.py` |
| `app/api/v1/docs_api.py` | `app/api/control/docs_api.py` |
| `app/api/v1/statistics_api.py` | `app/api/control/statistics_api.py` |
| `app/api/v1/admin_api.py` | `app/api/control/admin_api.py` |

> v4 中移除 `app/api/v1/` 中间目录。

### 2.2 接口能力迁移

- v3 单入口 `search` -> v4 三入口 search（按域）
- v3 单入口 `import` -> v4 三入口 import（按域）
- v3 统一 `download` -> v4 仅 `skill/memory` 可下载
- control 类 API 全部归档到 `/api/control/*`

---

## 3. Feature 结构迁移

### 3.1 顶层目录迁移

| v3 | v4 |
|---|---|
| `app/features/upload/` | `app/features/upload/` |
| `app/features/search/` | `app/features/search/`（内部结构重做） |
| `app/features/download/` | `app/features/download/`（按域拆分） |
| `app/features/docs|info|admin` | `app/features/control/*` |
| （无统一异步任务层） | `app/features/async_task/`（Celery 通用异步任务） |

### 3.2 import 子域迁移规则

v4 新增通用异步目录（import 的前置依赖）：

- `app/features/async_task/`
  - `service.py`（提交/查询/取消任务）
  - `tasks/dispatch_task.py`（Celery 通用消费入口）
  - `executors/registry.py`、`executors/upload_task_executor.py`（任务分发与 import 执行器）

v4 `app/features/upload/` 固定为：

- `knowledge_base_upload/`
- `skill_upload/`
- `memory_upload/`

每个子域都包含：

- `*_import_service.py`（API 入口服务）
- `parsers/parse_*.py`（统一对外 `parse`）
- `storage/store_*.py`（统一对外 `store`）

补充迁移约束：

- Import API 从“同步执行业务”迁移为“调用 `AsyncTaskService.submit(...)` 后返回 `202`”。
- 解析/入库由 Celery Worker 进程异步执行，不在 API 请求线程中完成。

### 3.3 search 子域迁移规则

v4 `app/features/search/` 固定为：

- `knowledge_base_search/`
- `skill_search/`
- `memory_search/`

每个子域都包含：

- `*_search_service.py`（API 入口服务）
- `searcher/search_*.py`（统一对外 `search`）

## 4. 基础设施层迁移

### 4.1 命名迁移

| v3 | v4 | 说明 |
|---|---|---|
| `app/infrastructure/storage/` | `app/infrastructure/file_system/` | 避免与 feature `storage/store_*.py` 混淆 |

### 4.2 调用迁移

- `skill_import` 与 `memory_import` 仍需：
  - 通过 `database/` 写数据库
  - 写本地或对象存储文件
- 文件写入统一经 `app/infrastructure/file_system/` 完成

---

## 5. KNOWLEDGE_BASE 特殊迁移

### 5.1 删除多仓储目录

v3 的：

- `features/search/repositories/`
- `features/upload/repositories/`

在 v4 中全部移除。

### 5.2 差异化能力替代方案

用“解析策略 + 检索策略”替代“repository 文件分叉”：

1. import 解析输出 `chunks`
2. 同时输出 `search_profile`
3. search 按 `search_profile` 生成检索语句

### 5.3 自定义脚本安全门禁

必须满足：

1. AST 检查通过
2. 容器隔离执行成功
3. 输出结构校验通过

任一失败都拒绝入库。

---

## 6. 分阶段迁移建议

### Phase 1：结构落地

- 创建 v4 API/Feature 目录骨架
- 引入新域枚举（`KNOWLEDGE_BASE/SKILL/MEMORY`）
- 增加 v3 -> v4 类型映射层

### Phase 2：能力迁移

- 拆分 search/import/download API
- 将 docs/statistics/admin 迁移到 control
- 替换 `infrastructure/storage` 引用为 `infrastructure/file_system`
- 接入 `features/async_task` 并完成 import API 的异步提交改造
- 增加 Celery Worker 部署与启动脚本（开发可用 eager/memory，生产使用独立 Worker）

### Phase 3：KNOWLEDGE_BASE 新机制

- 实现默认解析器适配层
- 实现 AST 安全检查
- 实现容器隔离执行器
- 接入 `search_profile` 存取与检索构建

### Phase 4：联调与回归

- API 契约联调
- 数据迁移与过渡验证
- 灰度发布与回退演练

---

## 7. 回退策略

- 迁移窗口期保留 v3 类型到 v4 类型的别名映射，稳定后清理
- control API 改造期间提供短期转发（可选）
- 对自定义解析脚本开关灰度发布，出现风险时可快速关闭
- 若 v4 `search_profile` 读取失败，临时回退到默认检索策略
